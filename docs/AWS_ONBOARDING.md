# AWS Account Onboarding

CloudSentinel uses a customer-controlled IAM role and STS AssumeRole for AWS assessment.

~~~text
CloudSentinel runtime
       |
       | sts:AssumeRole + ExternalId
       v
Customer AWS account
       |
       v
Read-only CloudSentinel role
       |
       v
AWS service configuration
~~~

CloudSentinel should not require customers to paste long-lived AWS access keys into the application.

## 1. Start CloudSentinel

~~~bash
docker compose up -d --build
docker compose exec api alembic upgrade head
~~~

Open http://localhost:8000, create a workspace and sign in.

## 2. Add the AWS account

Open **Cloud Accounts → Add AWS Account**.

Enter:

- Account name
- 12-digit AWS Account ID
- IAM Role ARN
- Region

Save the account.

CloudSentinel then shows:

- CloudSentinel principal ARN;
- generated External ID;
- current trust-policy template.

Use those exact values. Do not invent an External ID.

## 3. Create the read-only role in AWS

In the customer AWS account:

1. Open IAM.
2. Create a role that CloudSentinel can assume.
3. Configure its trust relationship using the principal ARN shown by CloudSentinel.
4. Require the External ID generated by CloudSentinel.
5. Attach the read-only permissions required by the enabled CloudSentinel scanners.

For an initial broad audit test, the AWS-managed SecurityAudit policy is the reference starting point. AWS describes it as providing access to read security configuration metadata for auditing software. citeturn1search0

Policy ARN:

~~~text
arn:aws:iam::aws:policy/SecurityAudit
~~~

For a hardened deployment, review the exact controls you enable and reduce permissions where practical. AWS notes that managed policies are not automatically least-privilege for every workload. citeturn1search1

### Trust policy

Do not copy a static example containing someone else's principal or External ID.

Use the **Copy Trust Policy** button in CloudSentinel. The application generates the current policy from the actual account connection.

Conceptually the trust relationship must contain:

- the CloudSentinel runtime principal;
- sts:AssumeRole;
- the CloudSentinel-generated External ID condition.

## 4. Test

Return to:

**Cloud Accounts → Setup → Test Connection**

A successful test confirms the role can be assumed and the AWS account identity matches the account ID stored in CloudSentinel.

If it fails, verify:

- role ARN;
- External ID;
- trust relationship principal;
- role read permissions;
- CloudSentinel runtime permission to call sts:AssumeRole.

Do not solve AssumeRole failures by granting broad administrator permissions.

## 5. Run the scan

Open **Overview → Run AWS Security Scan**, select the connected AWS account and start the scan.

The API queues the job and the worker performs the AWS collection/evaluation.

## 6. Understand results

### Findings

A finding is created from supported scanner evidence and includes the rule, affected resource, severity/risk context, evidence and remediation guidance where available.

### No findings

No findings is not automatically an error. If supported checks completed successfully and no implemented rule matched, an empty finding set can be valid.

### Warnings / partial coverage

If an AWS API call is denied or a regional/service check fails, CloudSentinel records the execution error/warning rather than pretending that the check was secure.

Always interpret findings together with scan status and execution errors.

## 7. Safety

The scanner is designed to assess configuration rather than change customer resources.

Before using CloudSentinel against an important account, review:

- IAM role permissions;
- enabled controls;
- regions to scan;
- data you are comfortable storing;
- retention/deletion requirements.

## 8. Disconnect

Use **Cloud Accounts → Delete** to remove an account connection and its associated scan/finding history from the CloudSentinel workspace.

Deleting the CloudSentinel connection does not delete the IAM role in the customer AWS account. Remove that AWS role separately if no longer required.

## 9. Multi-region

CloudSentinel supports multi-region scanning for supported services. Where regional isolation is implemented, a failed region does not automatically invalidate healthy regions. Review final scan warnings before treating a result as complete.

Never interpret an unscanned or permission-denied region as proof that no issue exists there.
