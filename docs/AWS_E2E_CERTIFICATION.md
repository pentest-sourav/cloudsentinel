# Real AWS E2E Certification

This gate is the next level above CI and credential-free launch certification. It
runs the signed production image against a **dedicated AWS certification account**
and requires CloudSentinel to prove the AWS identity before a scan is accepted.

## Security model

Use two IAM roles:

1. **GitHub OIDC runner role**
   - Trusted by GitHub Actions OIDC.
   - Restricted to this repository and the certification workflow/environment.
   - No broad AWS read permissions.
   - Allowed to call only `sts:AssumeRole` on the CloudSentinel scan role.

2. **CloudSentinel scan role**
   - Read-only permissions required by the scanners enabled in this release.
   - Trusted by the runner role.
   - Requires an `sts:ExternalId` beginning with `cs-aws-`.
   - Must not grant write, delete, IAM administration, billing mutation, or credential-management permissions.

The workflow uses short-lived OIDC credentials. Do not add static AWS access keys to
GitHub Secrets for this certification.

## GitHub OIDC trust boundary

The runner-role trust policy should constrain:

- OIDC issuer: `token.actions.githubusercontent.com`
- audience: `sts.amazonaws.com`
- repository: `pentest-sourav/cloudsentinel`
- the exact branch/environment used for the certification workflow.

**Important:** this repository was created after July 15, 2026. GitHub's current
default OIDC subject format therefore uses immutable owner/repository IDs. The
runner-role trust policy must use:

`repo:pentest-sourav@227156130/cloudsentinel@1376072200:ref:refs/heads/main`

For this certification workflow, the runner-role trust policy should be:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::997139435592:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:pentest-sourav@227156130/cloudsentinel@1376072200:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

Prefer a protected GitHub Environment such as `aws-certification` with required
reviewers before allowing the workflow to assume the AWS runner role. If an
environment is later added to the workflow, the OIDC `sub` value must be updated
to the environment subject format instead.

## Runner-role permissions

The runner role should be limited to the scan-role ARN:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::997139435592:role/CloudSentinel-Scan"
    }
  ]
}
```

Do not attach broad managed read-only policies to the runner role just to make the
workflow work. The runner is a credential broker, not the scanner.

## Scan-role trust boundary

The scan role should trust only the dedicated runner role and require the external
ID generated by CloudSentinel:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::997139435592:role/CloudSentinel-GitHubRunner"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringLike": {
          "sts:ExternalId": "cs-aws-*"
        }
      }
    }
  ]
}
```

The exact scanner permission set must come from the services/rules enabled in the
release. Do not blindly copy a broad `ReadOnlyAccess` policy into a customer
environment.

## What the certification proves

The workflow:

1. Accepts only an immutable `@sha256` image.
2. Verifies the image's Sigstore signature against the CloudSentinel release
   workflow identity.
3. Assumes the dedicated AWS runner role through GitHub OIDC.
4. Verifies the AWS account returned by STS matches the expected account ID.
5. Starts the production Compose graph.
6. Applies production migrations.
7. Tests the CloudSentinel AWS connection using the generated external ID.
8. Starts a real AWS scan.
9. Waits for the actual worker-backed scan to complete.
10. Rejects the certification if scanner execution errors are present.
11. Verifies persisted findings/summary data.
12. Verifies risk posture, dashboard aggregation, and the evidence-derived risk graph.
13. Runs the PostgreSQL backup/restore drill.
14. Uploads certification evidence.
15. Destroys the ephemeral certification stack.

No synthetic findings are created by the certification harness.

## Certification evidence

A successful run should record:

- immutable image digest;
- GitHub Actions run ID;
- AWS account ID and region;
- STS identity validation result;
- CloudSentinel scan ID;
- scan completion state;
- total findings and severity distribution;
- execution-error count;
- risk posture;
- dashboard validation;
- evidence-derived risk graph validation;
- backup and restore timings.

This evidence is stronger than a README claim: it demonstrates that the released
artifact actually reached AWS, executed the scanner, persisted the result, and
produced the production-facing security views.

## Important boundary

A green CI run is not an AWS certification.

A signed release is not an AWS certification.

The project should only describe the AWS path as **certified** after the workflow has
been executed successfully against the dedicated test account and the resulting
evidence has been retained.
