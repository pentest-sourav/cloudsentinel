# CloudSentinel

> **AWS-first Cloud Security Posture & Compliance Auditor**

CloudSentinel is an open-source, self-hosted cloud security platform that discovers AWS resources, evaluates security configurations, detects supported misconfigurations, produces evidence-backed findings, assesses contextual risk, and maps controls to compliance requirements.

> **Current focus:** AWS  
> **Azure:** Development phase  
> **Deployment model:** Self-hosted / controlled deployment  
> **Important:** CloudSentinel evaluates the AWS services and security controls implemented in this repository. It does not claim complete AWS Security Hub coverage, zero false positives, guaranteed compliance, or automatic detection of every possible AWS misconfiguration.

---

## What CloudSentinel does

CloudSentinel connects to an AWS account through a customer-controlled IAM role and STS AssumeRole. It is designed around a read-only assessment model.

~~~text
Customer AWS Account
        |
        | IAM role + External ID
        v
CloudSentinel
        |
        | STS AssumeRole
        v
AWS read-only APIs
        |
        v
Discovery / Collection
        |
        v
Security Rules
        |
        v
Evidence-backed Findings
        |
        +------> Risk assessment
        +------> Compliance mapping
        +------> Dashboard
        +------> HTML / PDF reports
~~~

A finding is based on scanner/collector evidence returned by the target AWS account. Permission-denied or failed checks are surfaced as scan execution errors/warnings rather than silently treated as secure.

# Quick Start

The easiest way to try CloudSentinel locally is Docker Compose. Docker Compose is designed to define a multi-container application and start the services together.

### Requirements

- Git
- Docker Engine
- Docker Compose v2
- 4 GB+ RAM recommended for a comfortable local run
- An AWS account is not required just to start the dashboard
- An AWS account and IAM role are required before running a real AWS scan

### 1. Clone

~~~bash
git clone https://github.com/pentest-sourav/cloudsentinel.git
cd cloudsentinel
~~~

### 2. Configure your local environment

~~~bash
cp .env.example .env
openssl rand -hex 32
~~~

Put the generated value into JWT_SECRET_KEY and set a strong POSTGRES_PASSWORD in .env.

Do not commit .env.

### 3. Start CloudSentinel

~~~bash
docker compose up -d --build
docker compose exec api alembic upgrade head
docker compose ps
~~~

Verify:

~~~bash
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8000/ready
~~~

Open the web console at:

~~~text
http://localhost:8000
~~~

The bundled web console is served by the API image, so a separate frontend development server is not required for the normal Docker setup.

### 4. Create your workspace

Open the dashboard and choose **Create account**.

Enter:

- Full name
- Organization
- Email
- Password

After registration, sign in and open **Cloud Accounts**.

# Connect an AWS account

CloudSentinel should not be given a customer's long-lived AWS access keys.

Instead, create a read-only IAM role in the AWS account being assessed and allow the CloudSentinel runtime principal to assume it with the External ID generated by CloudSentinel.

AWS documents SecurityAudit as an AWS managed policy intended for software that audits AWS account security configuration metadata. It can be attached to a role, although AWS recommends evaluating least-privilege requirements for the actual workload.

The dashboard guides you through the trust relationship:

1. Open **Cloud Accounts**.
2. Select **Add AWS Account**.
3. Enter the AWS account ID, role ARN, name, and region.
4. Save the account.
5. Copy the **CloudSentinel principal ARN** shown by the setup panel.
6. Copy the generated **External ID**.
7. Create/update the customer IAM role trust policy using those values.
8. Attach the required read-only permissions to the customer role.
9. Return to CloudSentinel and click **Test Connection**.
10. Start an AWS scan.

The setup panel provides the current trust policy generated by the application. Do not invent an External ID yourself.

See docs/AWS_ONBOARDING.md for the complete onboarding guide.

# What happens during a real scan?

After an AWS account is connected:

1. CloudSentinel validates the configured AWS account identity.
2. The API queues the scan.
3. A worker consumes the job from Redis.
4. AWS service collectors discover supported resources.
5. Security rules evaluate the collected configuration.
6. Evidence is persisted with the finding.
7. Risk and compliance context are calculated.
8. The dashboard shows the resulting findings.
9. Scan history and finding lifecycle data are retained for later comparison.

For example, if an implemented S3 control detects a public-access configuration, the resulting finding is tied to the AWS resource and the evidence returned by the scanner.

An empty finding list can also be a valid result when supported checks complete successfully and no implemented control is violated.

**Coverage is rule-based.** A service/configuration that is not covered by an implemented and tested control will not magically appear as a finding.

# Production / public deployment

The root docker-compose.yml is intended for local development.

For a controlled production-style deployment use:

~~~bash
docker compose -f deploy/docker-compose.prod.yml config -q
docker compose -f deploy/docker-compose.prod.yml pull
docker compose -f deploy/docker-compose.prod.yml up -d
~~~

The production deployment:

- uses an immutable CloudSentinel image;
- keeps PostgreSQL and Redis private;
- puts Caddy in front of the API;
- terminates HTTPS at Caddy;
- uses health/readiness checks;
- runs migrations before API/worker startup;
- uses a dedicated worker egress network for AWS API calls;
- does not mount developer AWS credentials;
- uses hardened container settings;
- supports authenticated Prometheus metrics;
- supports PostgreSQL backup and isolated restore procedures.

Production requires DNS pointing to the host and protected secrets.

See:

- docs/DEPLOYMENT.md
- docs/OPERATIONS_RUNBOOK.md
- docs/PRODUCTION_READINESS_AUDIT.md

**Do not expose PostgreSQL, Redis, or port 8000 directly to the Internet.**

# Security model

Current security controls include:

- tenant-scoped cloud accounts, scans, findings, reports and audit events;
- JWT authentication;
- Argon2 password hashing;
- role-based authorization;
- suspended-tenant token invalidation;
- Redis-backed rate limiting;
- request-size limits;
- trusted-proxy-aware client identification;
- security response headers;
- authenticated metrics;
- request correlation IDs;
- read-only AWS scanning;
- AWS account identity validation;
- evidence-backed findings;
- idempotent finding persistence;
- automated regression tests;
- dependency and container security gates in CI.

See docs/SAAS_READINESS.md for the current SaaS security/readiness position.

# Current project position

CloudSentinel should currently be presented as:

> **An AWS-first cloud security posture and compliance auditing platform with a launchable self-hosted web console.**

The current main branch is a production-grade controlled-deployment candidate, but target-environment production certification remains deployment-specific.

Do not claim:

- complete AWS Security Hub coverage;
- zero false positives;
- guaranteed compliance;
- enterprise CSPM replacement;
- measured production RPO/RTO without target-deployment evidence.
